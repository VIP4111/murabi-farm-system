# مراح بو علي

نظام إدارة مزرعة أغنام/ماعز (+نعام) شامل: سجل حيوانات، صحة وصيدلية،
تكاثر ونسب، علف، مالية وتحليل مالي، مهام فريق وبلاغات، تقارير، دليل
مبتدئ وتوجيه يومي، ودعم كامل لثلاث لغات (عربي، إنجليزي، هندية، أمهرية).

## التشغيل محلياً

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# عدّل .env حسب رغبتك (خصوصاً OWNER_PASSWORD وSECRET_KEY)

export FLASK_APP=run.py
flask db upgrade      # يطبّق كل المايجريشنز المسجَّلة بمجلد migrations/
flask seed             # ينشئ الصلاحيات، الأدوار الافتراضية، حساب المالك، الخدمات، والمحتوى المرجعي (أمراض/أعراض/دليل مبتدئ)

python run.py
```

افتح `http://127.0.0.1:5000` وسجّل دخول برقم الجوال وكلمة المرور اللي بملف `.env`.

## المايجريشنز (تعديل قاعدة البيانات)

المشروع يستخدم Flask-Migrate/Alembic — **أي تعديل على أي موديل بـ
`app/models/` لازم مايجريشن مرافق له**، ما فيه `db.create_all()` تلقائي.

```bash
# بعد أي تعديل موديل:
flask db migrate -m "وصف مختصر للتغيير"
# راجع الملف المولَّد بـ migrations/versions/ يدوياً قبل التطبيق —
# Alembic autogenerate مو مثالي 100% (خصوصاً مع تغييرات معقّدة كـ
# إعادة تسمية عمود، يكتشفها كـ"حذف+إضافة" بدل "تعديل").
flask db upgrade
```

**بالإنتاج (Render)**: `Procfile` يشغّل `flask db upgrade && flask seed`
تلقائياً بمرحلة "release" قبل كل نشر جديد — **لا تنسَ أبداً تكوّم
(commit) ملف المايجريشن الجديد مع كودك**، وإلا Render يطبّق كود بدون
الجدول المطلوب ويطيح بالتطبيق فور فتح أي شاشة تستخدم الموديل الجديد.

## الترجمة (3 لغات: إنجليزي، هندية، أمهرية)

كل نص عربي بالواجهة لازم يكون مُغلَّفاً بـ`{{ _('...') }}` (قوالب
Jinja) أو `gettext`/`lazy_gettext` (كود بايثون). دورة العمل القياسية
بعد إضافة نص جديد:

```bash
pybabel extract -F babel.cfg -k _l -o messages.pot .
pybabel update -i messages.pot -d app/translations
# اكتب الترجمات (راجع app/translations/*/LC_MESSAGES/messages.po
# للسلاسل الناقصة، أو استخدم apply_translations.py بالجذر لتطبيق
# قاموس {عربي: ترجمة} برمجياً — راجع الكوميتات السابقة لمثال حي)
pybabel compile -d app/translations
pytest -q -k translation_completeness   # يتأكد صفر سلسلة ناقصة
```

## سكربت المحاكاة التشغيلية (اختبار ميداني)

```bash
flask simulate-farm-month --days 30
```

يولّد نشاطاً واقعياً (شراء، تقريع، أمراض، إنجاز مهام) عبر نفس نقاط
الدخول الحقيقية بالنظام، ثم يرسل تقرير ملخص بالبريد لصاحب الحلال (لو
`RESEND_API_KEY` مضبوط).

> ⚠️ **تحذير صريح**: يكتب بيانات فعلية بقاعدة البيانات المتصلة —
> شغّله بس على قاعدة تطوير/اختبار محلية، **أبداً على قاعدة إنتاج
> حقيقية على Render**. لو شغّلته محلياً وتبي تنظّف بعده:

```bash
flask purge-simulation-data           # عرض فقط، صفر حذف
flask purge-simulation-data --yes     # حذف فعلي — يحذف حصراً سجلات
                                       # SIM- المولَّدة بالمحاكاة، صفر لمس لأي بيانات حقيقية
```

## العمل بدون اتصال (Offline Sync)

مبني بالكامل أصلاً — `app/static/sw.js` (Service Worker) +
`app/static/offline_sync.js` (طابور IndexedDB). أي نموذج فيه
`data-offline` كسمة (attribute) يشتغل تلقائياً بدون اتصال: يُخزَّن
الإدخال محلياً بالجهاز لو الاتصال مقطوع، ويُرسَل تلقائياً (fetch)
أول ما يرجع الاتصال — بدون أي تدخل من المستخدم. لإضافة نموذج جديد
لهذا السلوك، أضف `data-offline` على وسم `<form>` وخلاص.

**حدود الكاش الأوفلاين (SEC-01، تدقيق 2026-09-04)** — الكاش نطاقه الأصل
(origin) لا المستخدم، فعلى الجهاز المشترك كان العامل يرى صفحات المالك
المخزَّنة. خمس قواعد بـ`sw.js` تمنع ذلك:

1. **قائمة سماح** (default-deny): لا يُخزَّن أي ردّ إلا `/static/` — أصول
   ثابتة عامة لا تحمل هوية أحد. **صفر صفحات HTML.** جُرِّب أولاً استثناءٌ
   لخمس "صفحات ميدانية آمنة" (`/`، `/today`، `/alerts/mine`، `/team/tasks`،
   `/team/reports`) بحجة أن كل الأدوار تملك صلاحية فتحها، وأسقطه القياس
   الفعلي (2026-09-05): الخمسة تختلف بين حساب المالك وحساب العامل، وتحمل
   اسم المستخدم ورمز CSRF مرتبطاً بالجلسة. **اشتراك مستخدمَين بصلاحية فتح
   صفحة لا يثبت أن مشاركة ردّها بكاش واحد آمنة.** الدليل قابل لإعادة
   التشغيل: `bash tests/e2e/run_sw_e2e.sh --diff`.
2. أي مرور بـ`/login` أو `/logout` — أو ردّ أُعيد توجيهه لصفحة الدخول —
   **يمسح الكاش كاملاً**.
3. أي ردّ تنزيل (`Content-Disposition: attachment`) لا يُخزَّن.
4. **حارس الحقبة**: ردّ بدأ قبل المسح ووصل بعده لا يُكتب بالكاش.
5. عند حدّ المصادقة تُبلَّغ التبويبات المفتوحة فتعيد التحميل — منع التخزين
   وحده لا يمحو ما هو **معروض** بتبويب بقي مفتوحاً على صفحة المستخدم السابق.

**الأثر على الاستخدام (مقصود):** عرض الصفحات بلا اتصال لم يعد يعمل — لا
يمكن فتح شاشة إدخال من الصفر وأنت أوفلاين. **ما زال يعمل:** أي صفحة كانت
مفتوحة قبل الانقطاع، وطابور الإدخالات `data-offline` (IndexedDB) الذي
يخزّن ويعيد الإرسال تلقائياً — وهو القدرة الميدانية الحرجة. إعادة العرض
أوفلاين بأمان تحتاج تصميماً مستقلاً (كاش مقسَّم حسب المستخدم أو قشرة بلا
بيانات) وهي خارج نطاق هذه الدفعة.

**بعد النشر على جهاز مشترك:** الجهاز يبقى على الـSW القديم حتى يجلب
`/sw.js` المحدَّث. **الخروج والدخول وحدهما ليسا دليلاً** على الترقية — الـSW
القديم ينفّذهما بلا أي تغيير. للتحقق: الصق `tests/e2e/sw_post_deploy_check.js`
بوحدة تحكّم المتصفح على الجهاز نفسه وانتظر PASS.

**تنبيه مهم عند إضافة route جديد يُستخدم من نموذج `data-offline`**:
لازم يتبع نفس نمط إعادة التوجيه الموحَّد بالمشروع — فشل تحقّق =
`flash` خطأ + إعادة توجيه لنفس صفحة النموذج، نجاح = إعادة توجيه
لصفحة مختلفة (قائمة/تفاصيل). `offline_sync.js` يفرّق "نجاح" عن "فشل
تحقّق" بمقارنة رابط الرد النهائي بالرابط الأصلي — كسر هذا النمط
يعني بيانات المستخدم تُحذف من الطابور بصمت رغم إن السيرفر رفضها.

## متغيرات البيئة

### إلزامية

| المتغيّر | الوصف |
|---|---|
| `DATABASE_URL` | `sqlite:///farm_system.db` محلياً، رابط PostgreSQL حقيقي بالإنتاج (Render يحقنه تلقائياً لو ربطت قاعدة Postgres مُدارة) |
| `SECRET_KEY` | مفتاح جلسات عشوائي — **لازم قيمة حقيقية بأي نشر عام**، شاشة "فحص الجاهزية قبل النشر" ترصد بقاءه الافتراضي وتحذّر صراحة |
| `OWNER_NAME` / `OWNER_PHONE` / `OWNER_PASSWORD` | بيانات أول حساب مالك يُنشأ بأمر `flask seed` — غيّر `OWNER_PASSWORD` فوراً بعد أول دخول |

### اختيارية (كل ميزة تتجاهل نفسها بصمت بدون إعدادها — صفر كسر بالنظام)

| المتغيّر | الميزة |
|---|---|
| `TELEGRAM_BOT_TOKEN` | إشعارات تيليجرام الفورية (بلاغات، حالات طوارئ، تحصينات مستحقة) |
| `RESEND_API_KEY` + `EMAIL_FROM_ADDRESS` (+ `EMAIL_FROM_NAME` اختياري) | التقارير اليومية بالبريد + تقرير سكربت المحاكاة — عبر Resend (HTTPS API، مجاني حتى 100 بريد/يوم، بدون بطاقة). **لماذا API لا SMTP**: منافذ SMTP الصادرة محظورة على خطة Render المجانية |
| `CLOUDINARY_CLOUD_NAME` + `CLOUDINARY_API_KEY` + `CLOUDINARY_API_SECRET` | تخزين سحابي دائم للصور/الملفات الصوتية المرفوعة (بدونها: تخزين محلي مؤقت، يُفقَد عند كل إعادة نشر بخطة Render المجانية بدون قرص دائم) |
| `ANTHROPIC_API_KEY` + `ANTHROPIC_MODEL` | ترقية المساعد الذكي لفهم أسئلة حرة عبر Claude API (بدونهما: محرك محلي مبني على قاعدة معرفة ثابتة، يشتغل كامل بدون أي مفتاح) |
| `SESSION_COOKIE_SECURE` | يُفعَّل تلقائياً لما `RENDER` موجود بالبيئة (Render يحقنه هو تلقائياً) — كوكي الجلسة ما يُرسَل إلا عبر HTTPS |

### قبل أي نشر فعلي يصله مستخدمون حقيقيون

1. غيّر `SECRET_KEY` و`OWNER_PASSWORD` لقيم عشوائية حقيقية.
2. سجّل دخول وشغّل شاشة **"فحص الجاهزية قبل النشر"** بالإعدادات — تفحص كل هذا تلقائياً (كلمة مرور افتراضية، SECRET_KEY افتراضي، أمان الكوكي، نوع قاعدة البيانات، حظيرة عزل، فريق عمل...) وتعطيك قائمة حرجة/تحذيرات بدل ما تكتشفها بالطريقة الصعبة.
3. راجع شاشة **"فحص سلامة البيانات"** بالإعدادات — يكتشف سجلات يتيمة أو بيانات غير منطقية، مو أداة إصلاح تلقائي (عرض فقط عمداً — الإصلاح قرارك).

## الصيانة المستقبلية — إرشادات لإضافة ميزات جديدة بأمان

- **قاعدة البيانات**: أي موديل جديد أو حقل جديد = مايجريشن مرافق دائماً (`flask db migrate`)، راجعه يدوياً، واختبره محلياً (`flask db upgrade`) قبل الكوميت. الفهارس (`index=True`) على أي عمود FK يُستعلَم بكثرة (`animal_id`, `mother_id`...) أو عمود تاريخ يُرتَّب/يُفلتَر عليه كثيراً — أرخص وقت الإنشاء من إضافته لاحقاً على جدول كبير.
- **العمل بدون اتصال**: أي شاشة إدخال جديد يستخدمها العامل ميدانياً (بلاغ، مهمة، تسجيل حدث) — أضف `data-offline` على الفورم واتبع نمط إعادة التوجيه الموحَّد أعلاه. لا تبني منطق حفظ خاص يخالف النمط.
- **الترجمة**: أي نص عربي جديد بواجهة = `{{ _('...') }}` أو `_l()`/`gettext` فوراً وقت الكتابة، مو لاحقاً كدفعة منفصلة — تراكم النقص هو بالضبط اللي احتجنا نصلحه هذي الجلسة بجهد كبير.
- **البيانات المُخترعة ممنوعة**: أي رقم/توصية/محتوى طبي أو مالي يُعرض للمستخدم لازم يُشتق من بيانات فعلية مسجَّلة، أو يُترك فارغاً بوضوح ("تواصل للسعر"، "بدون قيمة تقديرية") — مبدأ التزمنا فيه بصرامة (راجع `lineage_service.py`, `zatca_service.py`, `feed_service.calculate_fcr_by_animal` كأمثلة موثَّقة).
- **الاختبارات**: `pytest -q` كامل قبل أي كوميت — 715 اختبار حالياً، صفر تسامح مع انحدار (regression).

## بنية المشروع (خريطة سريعة)

- `app/models/` — كل الموديلات (SQLAlchemy)، مقسَّمة حسب المجال (health، repro، finance، checklist، asset...).
- `app/<module>/routes.py` + `<module>_service.py` — كل وحدة (core، health، repro، finance، team، feed، reports، equipment، warehouses، climate، ostrich، batches، assistant، onboarding) لها Blueprint مستقل + منطق أعمال منفصل عن الراوت.
- `app/templates/` — قوالب Jinja، مقسَّمة بنفس بنية الوحدات.
- `app/translations/` — كتالوجات gettext (ar ضمني بالكود نفسه، en/hi/am مترجمة).
- `migrations/versions/` — تاريخ كامل لتطور قاعدة البيانات.
- `tests/` — 715 اختبار، `conftest.py` للـfixtures، `factories.py` لمصانع بيانات الاختبار.
- `app/cli.py` — أوامر إدارية (`flask seed`, `flask simulate-farm-month`, `flask purge-simulation-data`, `flask reset-password`, `flask telegram-updates`).
