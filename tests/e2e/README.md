# اختبارات القبول بمتصفح حقيقي (E2E)

اختبارات تحتاج متصفحاً وخادماً حيّاً، فلا يجمعها `pytest` تلقائياً بأسمائها
(بلا بادئة `test_`). تُشغَّل بأمر واحد يجهّز كل شي وينظّفه، وهي أيضاً جزء من
`pytest` عبر أغلفة تُتخطّى بسبب صريح حيث لا يتوفر Playwright/Chromium.

## التشغيل

```bash
# مرة واحدة
pip install -r requirements.txt playwright && playwright install chromium

# كل السيناريوهات
bash tests/e2e/run_sw_e2e.sh

# أو واحداً بعينه
bash tests/e2e/run_sw_e2e.sh --isolation
bash tests/e2e/run_sw_e2e.sh --upgrade
bash tests/e2e/run_sw_e2e.sh --queue
bash tests/e2e/run_sw_e2e.sh --diff

# داخل venv بلا تفعيل
PYTHON=.venv/bin/python bash tests/e2e/run_sw_e2e.sh
```

السكربت يجهّز قاعدة SQLite مؤقتة (مايجريشن + بذر + حساب عامل)، يشغّل
gunicorn على منفذ حر (`SW_E2E_PORT`، افتراضي 8099)، ينفّذ الاختبارات، ثم
يحذف كل شي — حتى عند الفشل. لا يلمس أي قاعدة بيانات أو منفذ لك.

يخرج بـ0 عند النجاح و1 عند اكتشاف تسريب — صالح كبوابة قبل النشر.

## السيناريوهات

| الملف | يثبت |
|---|---|
| `sw_cache_isolation_e2e.py` | العزل بين مستخدمي الجهاز الواحد: لا شاشة حسّاسة تُخزَّن، الكاش يُمسح عند الخروج، **رد محتجَز على مسار ضمن قائمة السماح لا يُكتب بالكاش بعد المسح** (سيناريو C — حارس الحقبة)، **وترتيب تبديل الهوية بخروج محتجَز: حجب فوري بلا إعادة قراءة، ثم إعادة تحميل بعد اكتمال الخروج** (سيناريو D)، ولا يُعرَض محتوى المالك للعامل تحت انقطاع الشبكة، **وأداة فحص ما بعد النشر تعطي PASS على جهاز مُحدَّث** (سيناريو E) |
| `sw_upgrade_e2e.py` | ترقية v7→v8 بكاش ملوّث وتبويبات مفتوحة تُزيل الكاش القديم بالكامل، وتوثّق متى يصبح الإصلاح فعّالاً |
| `offline_queue_across_users_e2e.py` | مسح الكاش لا يمسّ طابور الإدخالات غير المرسَلة (قبول SEC-01)، ويرصد أثر DATA-01 الباقي عند تبديل الحساب |
| `page_response_diff_e2e.py` | **دليل قرار قائمة السماح**: يقيس فرق الردّ الفعلي بين حساب مالك وحساب عامل للمسارات الخمسة التي كانت مستثناة، فيثبت أن كلاً منها يحمل بيانات جلسة/مستخدم ولا يصلح للمشاركة بكاش على مستوى الأصل (بلا متصفح — stdlib فقط) |

### أداة فحص ما بعد النشر

`sw_post_deploy_check.js` ليس سيناريو يُشغَّل بالسكربت، بل **مقتطف يلصقه
المستخدم بوحدة تحكّم المتصفح على الجهاز المشترك بعد النشر**. يطبع PASS/FAIL
بعد أن يفحص: أن الـSW نشط فعلاً، وأن الخادم يقدّم `murabi-offline-v9`، وأن
علامات الطبقات (ب)(د)(هـ) موجودة بالملف المُقدَّم، وأنه لا يوجد كاش باسم قديم،
ولا أي صفحة مخزَّنة خارج `/static/`.

**الخروج والدخول وحدهما ليسا دليلاً** على ترقية الجهاز — الـSW القديم
ينفّذهما بلا أي ترقية. الأداة نفسها مُختبَرة آلياً بسيناريو (E) داخل
`sw_cache_isolation_e2e.py`، فلا تُقدَّم كنصيحة غير مُتحقَّق منها.

## داخل pytest

`tests/test_sec01_e2e_browser.py` يشغّل السيناريوهات الأربعة كاختبارات pytest
عادية موسومة `e2e`. الثلاثة الأولى تعمل فعلياً بأي بيئة فيها Playwright
وChromium وحزمة gunicorn، وتُتخطّى **بسبب صريح يذكر الناقص بالاسم** حيث لا
تتوفر. سيناريو `--diff` لا يحتاج متصفحاً إطلاقاً فيعمل بمجرد توفّر gunicorn:

```bash
pytest -m e2e            # السيناريوهات الأربعة (~70 ثانية)
pytest -m "not e2e"      # كل شي عداها
```

الفحص على **الوحدات** لا على `PATH` — داخل venv بلا تفعيل يبقى `gunicorn`
مستورَداً وإن لم يكن ملفاً تنفيذياً بالمسار، والغلاف يمرّر `sys.executable`
للسكربت ليستخدم نفس البيئة.

## لماذا خارج CI الحالي

`.github/workflows/tests.yml` لا يثبّت Playwright ولا Chromium. البديل الآلي
الدائم الذي يعمل بكل تشغيلة CI:

- `tests/js/sw.test.js` — 51 اختباراً على منطق الـService Worker (قائمة
  السماح، حدود المصادقة ومرحلتيها وترتيبهما، حارس الحقبة، عدم تخزين
  التنزيلات، واستثناء التبويب المُنتقِل من التبليغ).
- `tests/test_sec01_sw_cache_isolation.py` — الجانب الخادمي وفحص الملف المُقدَّم.

لتشغيل E2E داخل CI مستقبلاً: أضف `pip install playwright && playwright install
--with-deps chromium` ثم `pytest -m e2e`. (بند C3 بجدول حواجز الإطلاق.)
